# F3 | Fit-Fin-Find — 금융 습관 기반 이성 매칭 테스터

가상의 나를 고르고 상황형 질문 10문항(답에 따라 달라지는 적응형)에 답하면 나의 **금융습관 페르소나**(16종)와 **재무 상태 유형**(6종)을 보여주고, 답변으로 파악한 이상형에 가까운 이성 후보 3명을 추천한 뒤, 고른 한 명과의 **궁합 점수**와 **추천 이유**를 보여주는 웹앱입니다.

> 모든 인물·금융 데이터는 가상으로 생성한 데이터입니다. 금융상품 추천이나 투자 조언을 하지 않습니다.

## 실행

Node.js 20 이상이 필요합니다.

```bash
npm install
npm run seed     # 목업 고객 3,000명 → data/f3.db (시드 고정, 매번 같은 데이터)
npm run dev      # http://localhost:3000
```

| 명령 | 설명 |
|---|---|
| `npm run seed` | 목업 DB 생성 + 분포 요약 + S2 추출 자체 점검 |
| `npm run build-persona` | `data/persona` 의 매핑 CSV 두 개를 합쳐 앱이 읽는 `customer_persona.csv` 생성 |
| `npm run verify` | 13,852명 모두 페르소나 판정 규칙이 매핑 결과와 같은지 검증하고 16종·재무 상태 6종 분포 출력 |
| `npm run audit` | 페르소나·재무 상태 분포와 둘의 교차표 출력. 규칙·경계값을 바꾸기 전후로 비교용 |
| `npm test` | Vitest 단위 테스트 (페르소나 판정 / 재무 상태 / 선호 벡터 / 궁합 / 추천 / 나이·지역 규칙) |
| `npx tsx scripts/verify-real-data.ts [csv]` | 실데이터 CSV 로 레벨·페르소나 분포와 추천 규칙을 점검 (DB 에 저장하지 않음) |
| `npm run build` · `npm run lint` | 프로덕션 빌드 · ESLint |

`better-sqlite3` 는 네이티브 모듈이라 설치한 OS에서만 동작합니다. WSL에서 설치했다면 WSL에서, Windows에서 실행하려면 Windows에서 `npm install` 을 다시 하세요.

## 환경변수

`.env.local` 에 넣습니다 (`.env.example` 참고).

| 변수 | 기본값 | 설명 |
|---|---|---|
| `ANTHROPIC_API_KEY` | 없음 | 없으면 추천 이유를 규칙 기반 문구로 만듭니다. 앱은 그대로 동작합니다. |
| `DB_SSL` | `false` | `true` 면 MySQL 접속에 TLS 를 씁니다. TiDB Cloud 처럼 TLS 를 요구하는 DB 에 필요합니다. |
| `LLM_MODEL` | `claude-sonnet-5-5` | 추천 이유 생성 모델 |

LLM 호출이 실패·거절되거나 15초를 넘기면, 또는 JSON 파싱이 두 번 실패하면 폴백 문구가 나갑니다. 응답의 `source` 가 `llm` / `fallback` 중 무엇인지 알려줍니다.

## 화면 흐름

`/` 시작 → `/me` 내 정보 → `/virtual` 가상의 나(카드에 페르소나·재무 상태 표시) → `/quiz` 질문 → `/recommend` 후보 3명 → `/match` 궁합 + 추천 이유

상태는 zustand 로 관리하고 `sessionStorage` 에 보관합니다(로그인 없음, 탭을 닫으면 사라짐). 앞 단계를 바꾸면 그 결과에 기대던 뒷 단계 상태는 자동으로 비워집니다.

## 페르소나 16종 · 재무 상태 6종

- **금융 습관 페르소나 16종**: 저축·소비·투자의 또래 대비 희소한 특징 중 주요 특징 1이 속한 그룹으로 정합니다. 판정 규칙은 `src/lib/assign.ts`. 후보 카드에는 주요 특징 2를 보조 성향 태그로 함께 보여 줍니다. 이름은 가칭이고 `src/lib/personas.ts` 에서 바꿉니다. 자세한 정의는 `data/persona/persona_v2_summary.md`.
- **재무 상태 6종**(`src/lib/finance.ts`): 또래 소득 5분위 − 재산 5분위의 차이(소득 쭉쭉형 · 소득 쑥쑥형 · 나란히형 · 자산 쑥쑥형 · 자산 쭉쭉형)와 무자산(잔고 점검형). 추천 후보 카드에 태그로 표시합니다.
- **데이터**: 앱은 MySQL 을 읽고 고객별 페르소나·특징·재무 상태는 `data/persona/customer_persona.csv` 에서 `customer_id` 로 붙입니다. 이 파일은 `data/persona/` 의 `persona_16_20_24_customer_mapping.csv` 와 `integrated_feature_df_8_vs_6_traits.csv` 에서 `npm run build-persona` 로 만듭니다. 파일이 없으면 API 가 안내 문구와 함께 503 을 돌려줍니다.
- 부채는 페르소나·재무 상태에 넣지 않았습니다(태그로 다룰 예정).
- 예전 5종(SAVER/PLANNER/GROWER/ENJOYER/DEBT)의 범위·일치도·2순위 방식과 "끌리는 유형" 배지, 유형 궁합 점수(M)는 없앴습니다.

## 실데이터 적용 기준 (`integrated_feature_df.csv`, 13,852명)

DB 에 연결하기 전에 `scripts/verify-real-data.ts` 로 추천 로직이 실데이터에서 동작하는지 점검했습니다(저장은 하지 않습니다). 목업 데이터가 아니라 이 CSV 를 쓸 때 아래 기준이 적용됩니다. 값이 기획서 초안과 다른 곳은 실데이터 분포에 맞춘 것이며, 모두 `config.ts` / `personas.ts` 에서 바꿀 수 있습니다.

**레벨 경계값** (`LEVEL_THRESHOLDS`)

| 축 | 기획서 초안 | 현재 | 근거 |
|---|---|---|---|
| 저축률 | 10%, 30% | **8%, 15%** | 초안 기준이면 낮음 44%, 높음 8% 로 쏠림. 현재는 거의 3등분 |
| 소비율 | 50%, 75% | **60%, 75%** | 중앙값 71%, p90 84% |
| 투자비율 | 10%, 25%, 45% | **4.5%, 5.4%, 6.2%** | 투자자(28%)의 비율이 2~9% 에 몰려 초안 기준에선 보통 이상이 0명. 투자자를 사분위로 나눔 |
| DSR | 20%, 40% | **15%, 25%** | 초안 기준에선 과부담 76명(0.5%). 25% 는 분포를 맞추기 위한 값이며 금융적 근거는 없음 |

**또래 기준 레벨** (`PEER_AGE_RANGE`, `realData.ts`)

추천이 나이가 비슷한 사람끼리 이뤄지므로, 실데이터의 저축·소비·투자·재산 레벨은 전체 고객이 아니라 **또래(본인 한국 나이 ±1세, 성별 무관) 안 위치**로 정합니다. 카드의 "또래 대비" 막대도 같은 또래를 씁니다.

| 축 | 레벨 기준 |
|---|---|
| 저축 | 또래 안 저축률 분위수. 경계는 위 8%, 15% 가 전체 고객에서 차지하는 분위(33.8, 66.7) |
| 소비 | 또래 안 소비율 분위수. 경계는 60%, 75% 의 전체 분위(31.1, 66.1) |
| 투자 | 또래 투자자 안 투자비율 분위수. 경계는 4.5%, 5.4%, 6.2% 의 투자자 내 분위(24.8, 48.9, 73.1). 미투자는 그대로 0 |
| 재산 | 또래 안 분위수 (이전에는 5세 연령대 안 분위수) |
| 소득 | 원본 `peer_income_percentile` (이미 ±1세 기준) |
| 부채 | DSR 절대 기준 15%, 25% 그대로 |

- 경계값(`LEVEL_THRESHOLDS`)을 바꾸면 그 값의 전체 분위가 다시 계산되어 또래 기준에도 그대로 반영됩니다.
- 추천 후보 나이 범위(`PARTNER_AGE_WINDOW`)는 성별에 따라 비대칭이라 레벨 기준으로 쓰지 않습니다. 그 범위로 재면 같은 나이·같은 값인데 성별에 따라 레벨이 달라집니다.
- **재산은 마이너스 현금을 0 으로 보고 다시 합산합니다**(`realData.ts` 의 `assetOf`). 원본 `total_asset` 은 부동산 + 주식 + 현금 + 예·적금 + 투자 예수금인데 `cash_balance` 가 6,451명(47%)에서 음수라, 대출이 없는데도 재산이 마이너스인 사람이 1,308명 있었습니다. 재산 분위수·레벨·카드 금액 모두 이 값을 씁니다.

**CSV → 고객 변환**
- 나이는 `korea_age`, 지역은 `region` 으로 거른 뒤 판단은 `region_merged` 로 합니다(광주·전남 → "광주", 전라북도 → "전북").
- 소득 구간은 CSV 의 `LOW / LOW_MID / MID / HIGH_MID / HIGH` 를 1~5 로 씁니다. 기획서의 연소득 구간 표와 정의가 다릅니다.
- 재산 레벨은 또래(한국 나이 ±1세) 안 분위수, 소득 레벨은 `peer_income_percentile` 입니다. 저축·소비·투자 레벨도 또래 안 분위수입니다(위 "또래 기준 레벨").
- 보조 태그(소비 방식·저축 스타일·포트폴리오·소득 안정성·비상자금·소비 분야·결제 수단)는 모두 삭제했습니다. 이전 점검 결과와 기준 논의는 이 문서에서 뺐고, 카드 태그는 재무 상태 유형입니다(부채 상태 태그는 정의 후 추가).
- 닉네임 자리에는 `name` 컬럼을 그대로 씁니다. 실명이 화면·LLM 입력으로 나가므로 실제 연결 전에 개인정보 관점의 점검이 필요합니다.

**추천 규칙** (`PARTNER_AGE_WINDOW`, `PARTNER_REGION_GROUPS`, `NEIGHBOR_REGIONS`)
- **가상의 나**: 성별·소득 구간은 정확히 일치, 같은 지역에서 나이 정확 일치 → 모자라면 ±1살 → (소규모 지역만) 인근 지역 정확 일치 → 인근 지역 ±1살. 그래도 모자라면 모자란 대로 보여줍니다.
- **상대 후보 나이**(한국 나이): 사용자가 여성이면 상대는 위 4살 ~ 아래 1살, 남성이면 위 3살 ~ 아래 4살. 후보가 모자라면 양쪽으로 1살씩만 넓힙니다. 나이는 하드 규칙이라 풀이 모자라면 나이를 풀지 않고 페르소나 조건만 풉니다.
- **상대 후보 지역**: 서울·경기 사용자는 서울·경기 모두, 그 외는 같은 지역만. **소규모 지역(세종·울산·제주)은 인근 지역까지** 허용합니다(세종→대전·충남·충북, 울산→부산·경남·경북, 제주→광주). 같은 지역 후보가 충분하면(10명 이상) 같은 지역만, 모자랄 때만 인근으로 넓힙니다. 인근 지역 목록은 임의 지정이니 서비스 기준에 맞게 바꾸세요.
- 소규모 지역을 고르고 `/me` 에서 다음을 누르면 "인근 지역 사람까지 찾아요" 안내 팝업이 뜹니다.
- 성별은 항상 다른 성별만 추천합니다.

**아직 하지 않은 것**
- 실데이터를 DB 에 적재하는 스크립트(CSV → `customers`), 앱 API 가 DB 대신 CSV 변환 결과를 읽게 하는 연결.
- 추천 결과 의견(만족/불만족, 불만족 시 소비·부채·저축·투자·소득·재산·지역·나이 선택) 수집 화면과 저장.
- CSV 에 없는 지표(소득 변동 지표, 저축 발생 개월 수)는 위 대체 값을 씁니다.

## 구현 결정 사항

기획서가 정하지 않았거나 모호했던 부분을 이렇게 정했습니다.

**데이터·레벨**
- **가처분소득 = 월소득 − 월소비.** 투자 축은 `월투자 / 가처분소득` 으로 계산합니다. 월소득 전체를 분모로 쓰면 "소비 적정 + 투자 매우 적극" 같은 조합이 예산 제약(소비+저축+투자+상환/12 ≤ 월소득×1.05) 안에 들어가지 못합니다.
- **분위수 축은 생성 후 다시 계산합니다.** 소득은 전체 3,000명, 재산은 연령대(23–29 / 30–34 / 35–39 / 40–45) 안에서의 분위수입니다. 그래서 §9.3의 "소득 구간 → income 레벨" 기본 매핑과 일부 어긋납니다(예: 3구간 하단은 하위).
- **예산 제약에 들어갈 수 없는 타깃 조합**(예: 높은 저축 + 과부담 상환)은 소비 → 저축 순으로 줄여 맞춥니다. 레벨과 페르소나는 원천 수치에서 다시 계산한 값이 정답이므로 타깃과 달라질 수 있습니다. 목업 생성기는 기획서 초안 경계값을 기준으로 만든 비율 범위를 쓰고 레벨은 현재 `config.ts` 경계값으로 다시 계산하므로, 목표 비율(22/30/18/20/10%)과 실제 분포는 `npm run seed` 요약에서 확인하세요.
- 닉네임 조합은 576가지라 3,000명 사이에 중복이 있습니다. 한 화면에는 같은 닉네임이 함께 나오지 않게 뽑습니다.

**매칭**
- **고객 3,000명을 한 번 읽어 메모리에서 매칭합니다.** 완화 단계와 가중 샘플링을 순수 함수로 두어 단위 테스트하기 위해서입니다. 기획서의 인덱스 두 개는 그대로 만들어 둡니다.
- **S2 완화(목업·기본 모드)**는 엄격한 단계에서 찾은 사람을 먼저 채우고 모자란 만큼만 다음 단계에서 보충합니다. 5차까지도 모자라면(입력 나이가 23–45세 밖일 때) 같은 성별에서 나이가 가까운 순으로 채웁니다. 입력 나이는 20–49세를 받습니다.
- **S5 샘플링 가중치는 P³** 입니다. 상위 15명의 P가 서로 비슷해 P에 그대로 비례시키면 사실상 균등 추첨이 되기 때문입니다. `RECOMMEND.weightPower` 를 1로 바꾸면 기획서 원문대로입니다.
- 이성 후보는 페르소나로 거르지 않습니다. 성별·지역·나이 규칙을 통과한 사람 중에서 선호 적합도 P로 뽑습니다.
- "다시 뽑기 / 다른 후보 보기"는 이미 본 사람을 제외하며, 남은 인원이 모자라면 다시 포함합니다.

**점수**
- **총점은 정수로 반올림한 하위 점수(P/H/L)의 가중합**입니다. 화면에 보이는 숫자로 총점을 검산할 수 있습니다. 유형 점수(M)를 없애면서 가중치를 임시로 P 0.27 · H 0.60 · L 0.13 으로 맞췄습니다(기존 비율의 비례 조정).
- P는 6축 선호와 후보 레벨의 거리만으로 계산합니다(태그 선호 삭제). 축 선호가 하나도 없으면 중립값 50입니다. (10문항 모두 답해야 하므로 실제로 일어나지 않습니다.)

**화면**
- 결과 레이더에서 응답이 없는 축은 가운데(50)에 두고 축 이름 아래 "상관없음"을 적습니다.
- 축마다 레벨 수가 달라 레이더·미니 막대는 0–100으로 정규화해 그립니다. 수치는 보여주지 않고 라벨만 보여줍니다.
- 하위 점수 막대와 6축 미니 막대는 CSS로, 레이더만 Recharts로 그렸습니다.
- `/api/questions` 는 문항 문구만 내려주고 축 매핑(`effects`)은 서버에만 둡니다.
- 10문항 모두 답해야 결과를 볼 수 있습니다(`QUIZ.minAnswers`). 10번째 문항까지 갔는데 건너뛴 문항이 있으면 그 목록을 보여주고 돌아가 답하게 합니다.

**LLM**
- 기획서대로 `ANTHROPIC_API_KEY` 가 있을 때만 호출합니다. 요청에는 `output_config: { effort: 'low' }` 를 넣었습니다(15초 제한 안에 끝내기 위함). 이 옵션을 지원하지 않는 구형 모델을 `LLM_MODEL` 로 지정하면 호출이 실패해 폴백 문구가 나갑니다.
- 거절 시 다른 모델로 넘기는 서버 측 fallback 옵션은 쓰지 않았습니다. 모델이 환경변수로 바뀔 수 있고, 어떤 실패든 규칙 기반 문구로 대체되기 때문입니다.
